1. Цель работы

Исследовать влияние ограниченного объёма SRAM микроконтроллера Arduino Uno на выполнение рекурсивных функций, определить признаки возможного переполнения стека и сравнить рекурсивный алгоритм с итерационным решением, расход стека которого остаётся приблизительно постоянным.

2. Теоретическая часть

Микроконтроллер ATmega328P, используемый в Arduino Uno, имеет 2 КБ SRAM (2048 байт). В SRAM размещаются:

• Статические данные — глобальные и статические переменные, а также служебные данные.
• Куча (heap) — область динамически выделяемой памяти.
• Стек (stack) — адреса возврата, локальные переменные, аргументы и сохранённые регистры функций.

При рекурсивном вызове функции создаётся новый стековый кадр. Пока предыдущие вызовы не завершились, их кадры остаются в памяти. Поэтому при глубокой рекурсии расход стека увеличивается.

Приближённая оценка допустимой глубины рекурсии:

N ? (2048 ? статические данные ? исходный стек ? резерв) / размер одного кадра

Точный размер кадра зависит от кода, компилятора, локальных переменных, аргументов и сохранённых регистров. Поэтому расчёт без анализа файла компилятора .su является оценочным.

3. Эксперимент № 1. Рекурсивный вызов

Методика

В Wokwi был создан проект Arduino Uno. В программе использована функция deepRecursion(), которая вызывает сама себя с увеличением параметра depth. Для увеличения размера стекового кадра применён локальный массив localData[16]. Вывод в Serial Monitor выполнялся каждые десять уровней.

Предварительный прогноз

Ожидалось, что глубина вызовов будет увеличиваться до тех пор, пока доступной SRAM не станет недостаточно. Возможные проявления: зависание, перезапуск, прекращение или искажение вывода. Конкретное значение глубины заранее определить точно нельзя.

Фактическое наблюдение

В Serial Monitor были замечены строки START, 10, после чего появился некорректный символ r. Автоматическая перезагрузка контроллера не была подтверждена. После наблюдения симуляция была остановлена вручную примерно через две минуты.

Последнее корректно отображённое значение глубины: 10 (по имеющемуся наблюдению).
Наблюдаемый симптом: после вывода 10 появился некорректный символ; дальнейшее корректное увеличение глубины не зафиксировано.
Доказательство: screenshots/crash_result.png (если файл находится в другой папке репозитория, путь следует поправить).

Анализ

Наблюдаемое искажение вывода может быть связано с нарушением работы программы при исчерпании доступной памяти, однако один некорректный символ сам по себе не доказывает переполнение стека. На результат также могли повлиять служебные расходы Serial, особенности компиляции и распределение SRAM. Для строгого подтверждения требуются повторный запуск и сопоставление поведения с доступной памятью.

4. Эксперимент № 2. Итерационная версия

Методика

Рекурсивная функция была заменена циклом for, который выполняет 10 000 итераций. Значения выводились с шагом 1000.

Фактический результат

В Serial Monitor были получены значения от 1000 до 10000, после чего появилась строка DONE. Программа завершила выполнение цикла.

Результат: 10 000 итераций выполнены успешно.
Доказательство: screenshots/safe_result.png (при необходимости уточнить фактическое имя файла).

Объяснение

В итерационном варианте не создаётся новая цепочка одновременно активных вызовов функции на каждом шаге. Поэтому расход стека не увеличивается пропорционально количеству итераций и остаётся приблизительно постоянным. Сам цикл всё равно использует стек для работы функции и временных данных, поэтому утверждать, что стек не используется вообще, неправильно.

5. Эксперимент № 3. Memory Hog

По методическим указаниям этот этап должен выполняться с рекурсивной функцией memoryHog(uint8_t level) и локальным массивом volatile int buffer[300]. Необходимо последовательно проверить уровни от 0 до 4, каждый раз перезапуская симуляцию, и записать фактическое поведение.

Оценка памяти только для массивов:

|Уровень|Число одновременно активных массивов|Оценка памяти массивов|
|------:|-----------------------------------:|---------------------:|
|0      |1                                   |около 600 байт        |
|1      |2                                   |около 1200 байт       |
|2      |3                                   |около 1800 байт       |
|3      |4                                   |около 2400 байт       |
|4      |5                                   |около 3000 байт       |

Оценка основана на размере int 2 байта на ATmega328P: 300 ? 2 = 600 байт на один массив. Реальный расход больше, поскольку каждый стековый кадр также содержит адрес возврата, локальные данные, сохранённые регистры и другие служебные сведения.

Важно для завершения отчёта: в ходе переписки для этого этапа первоначально был предложен отдельный пример с malloc(). Он не соответствует методике Memory Hog из задания, поэтому результат такого примера нельзя выдавать за результат требуемого рекурсивного эксперимента. Перед сдачей необходимо выполнить именно вариант с memoryHog() и заполнить таблицу фактическими наблюдениями.

|Проверяемый уровень|Фактический результат      |
|------------------:|---------------------------|
|0                  |Заполнить по Serial Monitor|
|1                  |Заполнить по Serial Monitor|
|2                  |Заполнить по Serial Monitor|
|3                  |Заполнить по Serial Monitor|
|4                  |Заполнить по Serial Monitor|

Доказательство: screenshots/memory_hog_result.png — приложить скриншот именно требуемого рекурсивного эксперимента.

7. Инженерный вывод

Arduino Uno имеет небольшой объём SRAM, поэтому при разработке встроенных программ необходимо учитывать не только размер глобальных переменных, но и расход стека и кучи. Рекурсивные функции могут создавать множество одновременно активных стековых кадров, что повышает риск исчерпания памяти. Фактическое поведение при нехватке памяти не обязано проявляться только перезагрузкой: возможны зависание, искажение данных или прекращение вывода. Итерационный алгоритм в рассмотренном примере выполнил 10 000 шагов, при этом количество одновременно активных вызовов не увеличивалось на каждом шаге. Следовательно, для микроконтроллеров с ограниченной SRAM предпочтительно контролировать глубину рекурсии и по возможности использовать итерационные алгоритмы. Эксперимент Memory Hog должен дополнительно подтвердить влияние нескольких одновременно активных стековых кадров.
